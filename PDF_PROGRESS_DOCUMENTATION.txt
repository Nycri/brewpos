SECTION 2: SYSTEM OVERVIEW
================================================================================
2.1 Purpose:
    BrewPOS is an enterprise-grade, lightweight Point-of-Sale (POS) and inventory
    cataloging system designed for specialty coffee shops. The system demonstrates
    the practical synthesis of relational database management principles (3NF normalization,
    declarative referential integrity, composite primary keys, least-privilege role
    security) and modern web application development (Spring Boot REST APIs, declarative
    transactions, and vanilla JavaScript client-side state management).

2.2 Relationship to Approved Activity 2 Proposal:
    BrewPOS directly implements the data architecture and transactional requirements
    formulated in the approved Activity 2 proposal:
    - Implements the approved five-table relational model without altering table counts,
      relationships, or cardinalities.
    - Preserves the domain rule regarding monetary totals: No derived grand totals or line
      subtotals are persisted in database columns. All monetary figures are calculated
      dynamically via SQL aggregates (`SUM(quantity * sold_price)`) to guarantee data
      normalization and eliminate data synchronization anomalies.
    - Enforces the approved historical price isolation rule: Menu item prices can change
      over time, but once a sale is finalized, the unit price at the time of purchase is
      captured into `order_line_item.sold_price`, keeping past financial receipts immutable.

2.3 System Scope & Boundaries:
    - Included Capabilities:
      1. Front-of-House Register: Rapid menu browsing by category, search-as-you-type,
         cart assembly with automatic duplicate line merging, Tender selection (Cash / Online),
         and single-transaction ticket creation.
      2. Menu Catalog Management: CRUD on menu categories, menu item creation/editing,
         price adjustments, and activation/deactivation toggles (soft-hide from register).
      3. Transaction History & Receipts: Chronological audit trail of order tickets with
         date range filtering (`[start, end)`) and itemized modal receipt views.
      4. Daily Sales Analytics: PostgreSQL aggregation of daily gross sales, transaction
         counts, and payment method breakdowns (Cash vs. Online share).
    - Deliberate Scope Exclusions (per course specification):
      Employee password authentication (replaced with intuitive role-switching UI for demo),
      multi-tier tax formulas, discount vouchers, split billing, inventory supply tracking,
      and post-settlement order modifications/cancellations.

3.2 Role Separation Security Architecture:
    - Application Layer: Staff members interact with the POS using a lightweight,
      session-persistent top-right selector (`Demo Cashier` vs. `Demo Manager`). When in
      Cashier mode, product pricing forms and category modification tools are removed
      from the DOM, preventing unauthorized modifications.
    - Database Layer: The Spring Boot application authenticates using the dedicated
      `brewpos_app` login role. Database-level permissions strictly deny `UPDATE` and
      `DELETE` on `order_ticket` and `order_line_item`, guaranteeing that even if a
      malicious HTTP request bypasses the web front-end, historical sales records cannot
      be deleted or modified at the database engine level.

5.1 Entity-Relationship Diagram (ERD):

         +--------------------+              +--------------------+
         |       staff        |              |   menu_category    |
         +--------------------+              +--------------------+
         | PK  staff_id (SER) |              | PK  category_id(SER|
         |     full_name (VC) |              | UQ  category_name  |
         |     role (VC)      |              +--------------------+
         +---------+----------+                        |
                   | 1                                 | 1
                   |                                   |
                   | handles                           | groups
                   |                                   |
                   | N                                 | N
         +---------v----------+              +---------v----------+
         |    order_ticket    |              |     menu_item      |
         +--------------------+              +--------------------+
         | PK  order_id (SER) |              | PK  item_id (SER)  |
         | FK  staff_id (INT) |              | FK  category_id(INT|
         |     order_timestamp|              |     item_name (VC) |
         |     payment_method |              |     price (DEC)    |
         +---------+----------+              |     is_active (BOL)|
                   | 1                       +---------+----------+
                   |                                   | 1
                   | contains                          |
                   |                                   | sold in
                   | N                                 |
         +---------v-----------------------------------v----------+
         |                    order_line_item                     |
         +--------------------------------------------------------+
         | PK, FK  order_id   (INTEGER)                           |
         | PK, FK  item_id    (INTEGER)                           |
         |         quantity   (INTEGER)                           |
         |         sold_price (DECIMAL(10,2))                     |
         +--------------------------------------------------------+

5.2 Database Schema Summary:
    Database Name: `grp_brewposdb` | Schema: `public` | RDBMS: PostgreSQL 18.6
    1. `staff`: 3 columns (`staff_id`, `full_name`, `role`).
    2. `menu_category`: 2 columns (`category_id`, `category_name`).
    3. `menu_item`: 5 columns (`item_id`, `category_id`, `item_name`, `price`, `is_active`).
    4. `order_ticket`: 4 columns (`order_id`, `staff_id`, `order_timestamp`, `payment_method`).
    5. `order_line_item`: 4 columns (`order_id`, `item_id`, `quantity`, `sold_price`).
       *Total Tables: Exactly 5 tables. Zero surrogate keys on line items.*

5.3 SQL Scripts and Migrations Manifest:
    - `database/schema.sql`: Authoritative schema creation DDL.
    - `database/seed.sql`: Idempotent reference catalog and sample orders seeder.
    - `database/05_create_app_role.sql`: Application runtime role creation script.
    - `database/03_verification_queries.sql`: DBA verification query suite.
    - `database/06_align_existing_db.sql`: Database migration alignment script.

5.4 Seed Data Description:
    - Staff: 1 Cashier (`Demo Cashier`), 1 Manager (`Demo Manager`).
    - Categories: `Coffee`, `Non-Coffee`, `Pastries`.
    - Menu Items: 10 active items ranging from 60.00 to 130.00; 1 inactive item
      (`Pumpkin Spice Latte`, 140.00) specifically seeded to test POS exclusion.
    - Sample Orders: 5 historical orders (3 today, 2 yesterday) capturing both Cash
      and Online tender to provide immediate validation data for sales reports.

5.5 Design Evolutions & Justifications:
    - Decision: Use composite primary key `(order_id, item_id)` instead of a surrogate `line_id`.
      *Reason:* Natural 3NF model; natively prevents duplicate lines for the same product
      on a single receipt while reducing index overhead.
    - Decision: Store `sold_price` directly on `order_line_item`.
      *Reason:* Protects historical financial data from future catalog price changes.
    - Decision: Never persist derived subtotals or order grand totals.
      *Reason:* Eliminates write synchronization anomalies; computes dynamically on read.

SECTION 8: ISSUES AND RESOLUTIONS
================================================================================
1. Issue: Retrospective Alteration of Past Order Totals on Menu Price Changes
   - Problem: If an item's selling price is modified, joining `order_line_item` to
     `menu_item.price` alters past receipts and misstates financial history.
   - Resolution: Added `sold_price DECIMAL(10,2)` directly to `order_line_item`. The
     backend snapshot copies the menu item's active price into `sold_price` at checkout,
     permanently insulating historical receipts from catalog updates.

2. Issue: Primary Key Violations on Repeated Cart Clicks
   - Problem: Clicking the same product multiple times produced multiple payload lines
     with identical `item_id`, violating composite PK `(order_id, item_id)`.
   - Resolution: Implemented duplicate line merging in both the client-side cart (`pos.js`)
     and server-side order processor (`OrderService.java`) using a `LinkedHashMap` with
     `Math::addExact` to combine quantities into a single persistent row.

3. Issue: IEEE 754 Floating-Point Inaccuracies in Client-Side Money Formatting
   - Problem: JavaScript standard numeric operations produced rounding artifacts (e.g.,
     `0.1 + 0.2 = 0.30000000000000004`).
   - Resolution: Centralized all monetary arithmetic in integer cents (`toCents`,
     `formatMoneyFromCents` in `api.js`). In Java, all calculations use `BigDecimal`
     with explicit scale 2 and `RoundingMode.HALF_UP`.

4. Issue: Asynchronous Race Conditions in Date Range Filtering
   - Problem: Rapid consecutive clicks on date filters (e.g., clicking "Today" then "All")
     caused out-of-order fetch resolutions, overwriting the UI with stale records.
   - Resolution: Introduced monotonic request sequence counters (`listRequestSeq`,
     `reportRequestSeq`). Incoming HTTP responses check if their sequence matches the
     latest request; obsolete asynchronous responses are safely discarded.

5. Issue: Non-JSON Payloads Triggering Misleading HTTP 500 Responses
   - Problem: Sending requests with wrong `Content-Type` headers was captured by the
     generic `Exception.class` handler, falsely reporting server crashes (HTTP 500).
   - Resolution: Added explicit `@ExceptionHandler(HttpMediaTypeNotSupportedException.class)`
     returning HTTP 415 (`Unsupported Media Type`) with sanitized error messaging.
