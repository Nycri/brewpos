1.2 .ENV.EXAMPLE SPECIFICATION & ENVIRONMENT MANAGEMENT
--------------------------------------------------------------------------------
Purpose:
Defines the environment variable contracts required by Spring Boot without exposing
confidential credentials in the version control repository.

Key Variables:
- DB_URL: JDBC connection string to the local PostgreSQL database
  Default: jdbc:postgresql://localhost:5432/grp_brewposdb
- DB_USERNAME: Database username (defaults to 'postgres' for local testing or
  'brewpos_app' for least-privilege production runtime).

  must be configured only in the local, git-ignored `.env` file.

Security & Format Rules:
- The actual `.env` file is explicitly ignored in `.gitignore` to prevent credential leakage.
- Values follow Java properties syntax (no quotes around strings, backslashes escaped).
- Spring Boot loads the file via: `spring.config.import=optional:file:.env[.properties]`.

1.5 COMPREHENSIVE DATABASE DOCUMENTATION
--------------------------------------------------------------------------------
Database Engine: PostgreSQL 18.6 (compatible with PostgreSQL 16+)
Target Database: `grp_brewposdb`
Schema: `public`
Design Philosophy: Third Normal Form (3NF), strict referential integrity, immutable historical prices.

Relational Table Specifications:
1. Table `staff`:
   - staff_id (SERIAL, PK): Unique staff identifier.
   - full_name (VARCHAR(100), NOT NULL): Employee full name.
   - role (VARCHAR(20), NOT NULL): Role designation.
   - Constraint: `chk_staff_role CHECK (role IN ('CASHIER', 'MANAGER'))`.

2. Table `menu_category`:
   - category_id (SERIAL, PK): Unique category identifier.
   - category_name (VARCHAR(50), NOT NULL, UNIQUE): Unique name of the category.
   - Constraint: `uq_menu_category_name UNIQUE (category_name)`.

3. Table `menu_item`:
   - item_id (SERIAL, PK): Unique menu item identifier.
   - category_id (INTEGER, NOT NULL, FK -> menu_category.category_id): Parent category.
   - item_name (VARCHAR(100), NOT NULL): Product name.
   - price (DECIMAL(10,2), NOT NULL): Current selling price.
   - is_active (BOOLEAN, NOT NULL, DEFAULT TRUE): Flag controlling visibility on POS register.
   - Constraints:
     * `fk_menu_item_category FOREIGN KEY (category_id) REFERENCES menu_category(category_id)`
     * `chk_menu_item_price CHECK (price >= 0)`
     * `uq_menu_item_category_name UNIQUE (category_id, item_name)`

4. Table `order_ticket`:
   - order_id (SERIAL, PK): Unique receipt/ticket transaction identifier.
   - staff_id (INTEGER, NOT NULL, FK -> staff.staff_id): Staff member recording the transaction.
   - order_timestamp (TIMESTAMP, NOT NULL, DEFAULT CURRENT_TIMESTAMP): Transaction timestamp.
   - payment_method (VARCHAR(20), NOT NULL): Payment tender type.
   - Constraints:
     * `fk_order_ticket_staff FOREIGN KEY (staff_id) REFERENCES staff(staff_id)`
     * `chk_order_ticket_payment CHECK (payment_method IN ('CASH', 'ONLINE'))`

5. Table `order_line_item`:
   - order_id (INTEGER, NOT NULL, FK -> order_ticket.order_id): Order ticket reference.
   - item_id (INTEGER, NOT NULL, FK -> menu_item.item_id): Menu item reference.
   - quantity (INTEGER, NOT NULL): Units purchased.
   - sold_price (DECIMAL(10,2), NOT NULL): Historical unit price at checkout time.
   - Constraints:
     * `pk_order_line_item PRIMARY KEY (order_id, item_id)` (Composite Primary Key)
     * `fk_order_line_order FOREIGN KEY (order_id) REFERENCES order_ticket(order_id)`
     * `fk_order_line_item FOREIGN KEY (item_id) REFERENCES menu_item(item_id)`
     * `chk_order_line_quantity CHECK (quantity > 0)`
     * `chk_order_line_sold_price CHECK (sold_price >= 0)`

Database Indexes:
- `idx_order_ticket_timestamp` on `order_ticket(order_timestamp)`:
  Optimizes date range queries (`[start, end)`) for Daily Sales reports and Order History.
- `idx_order_line_item_item_id` on `order_line_item(item_id)`:
  Optimizes item lookup performance and foreign key validation when deactivating/deleting catalog items.

Dynamic Total Calculation Formula:
Subtotal = quantity * sold_price
Order Total = SUM(order_line_item.quantity * order_line_item.sold_price)
Daily Sales = SUM(order_line_item.quantity * order_line_item.sold_price) for all orders in date range.

1.7 USER AND ROLE SETUP DOCUMENTATION (POSTGRESQL RBAC)
--------------------------------------------------------------------------------
This section documents the intended PostgreSQL Group Roles, Login Accounts, and
Privilege Grids designed to enforce the Principle of Least Privilege:

1. Group Roles (NOLOGIN):
   - `app_runtime_grp`: Grants operational read/write access required for daily sales.
   - `app_readonly_grp`: Grants read-only access for reporting and auditing.
   - `app_admin_grp`: Grants catalog management privileges without database superuser status.

2. Login Accounts (WITH LOGIN):
   - `brewpos_app`: Member of `app_runtime_grp`. Used by Spring Boot `.env`.
   - `brewpos_auditor`: Member of `app_readonly_grp`. Used for external reporting.
   - `brewpos_admin`: Member of `app_admin_grp`. Used for catalog maintenance.

3. Role Setup & DCL Scripts (Executed in psql):
   ```sql
   -- Create Group Roles
   CREATE ROLE app_runtime_grp  WITH NOLOGIN;
   CREATE ROLE app_readonly_grp WITH NOLOGIN;
   CREATE ROLE app_admin_grp    WITH NOLOGIN;

   -- Table-Level Grants for app_runtime_grp
   GRANT CONNECT ON DATABASE grp_brewposdb TO app_runtime_grp;
   GRANT USAGE ON SCHEMA public TO app_runtime_grp;
   GRANT SELECT ON public.staff TO app_runtime_grp;
   GRANT SELECT, INSERT, UPDATE, DELETE ON public.menu_category, public.menu_item TO app_runtime_grp;
   GRANT SELECT, INSERT ON public.order_ticket, public.order_line_item TO app_runtime_grp;
   GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_runtime_grp;

   -- Table-Level Grants for app_readonly_grp
   GRANT CONNECT ON DATABASE grp_brewposdb TO app_readonly_grp;
   GRANT USAGE ON SCHEMA public TO app_readonly_grp;
   GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_readonly_grp;

   -- Table-Level Grants for app_admin_grp
   GRANT CONNECT ON DATABASE grp_brewposdb TO app_admin_grp;
   GRANT USAGE ON SCHEMA public TO app_admin_grp;
   GRANT SELECT ON public.staff TO app_admin_grp;
   GRANT ALL PRIVILEGES ON public.menu_category, public.menu_item TO app_admin_grp;
   GRANT SELECT ON public.order_ticket, public.order_line_item TO app_admin_grp;
   GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_admin_grp;

   -- Create Dedicated Login User (Placeholder password pattern)
   CREATE ROLE brewpos_app WITH LOGIN PASSWORD 'CHANGE_IN_LOCAL_ENV';
   GRANT app_runtime_grp TO brewpos_app;

   CREATE ROLE brewpos_auditor WITH LOGIN PASSWORD 'CHANGE_IN_LOCAL_ENV';
   GRANT app_readonly_grp TO brewpos_auditor;
   ```

Security Note on Completed Orders:
`order_ticket` and `order_line_item` are strictly granted `SELECT, INSERT` to runtime
accounts. `UPDATE` and `DELETE` are omitted, guaranteeing that past sales cannot be
tampered with, altered, or deleted through application runtime queries.

1.8 TROUBLESHOOTING GUIDE & COMMON SETUP ERRORS
--------------------------------------------------------------------------------
1. Error: "psql: error: connection to server at 'localhost' (127.0.0.1), port 5432 failed: Connection refused"
   - Cause: The PostgreSQL service is stopped or running on a non-default port.
   - Solution: Start PostgreSQL via Windows Services (`services.msc` -> `postgresql-x64-18`)
     or check your active port using `netstat -ano | findstr 5432`. Update `DB_URL` in `.env` if using port 5433.

2. Error: "FATAL: password authentication failed for user 'postgres'"
   - Cause: The password entered in `.env` does not match your local database password.
   - Solution: Open `.env` and verify `DB_PASSWORD=your_actual_password`. Ensure no trailing spaces or quotes.

3. Error: "Access is denied" or PowerShell script execution failure on `mvnw.cmd`
   - Cause: Restricted PowerShell ExecutionPolicy or OneDrive path reparse point lock.
   - Solution: Run PowerShell as Administrator and execute:
     `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass`
     Then re-run `.\mvnw.cmd spring-boot:run`.

4. Error: "JAVA_HOME is not defined correctly"
   - Cause: Maven Wrapper cannot locate a valid JDK 17+ installation.
   - Solution: Set your session JAVA_HOME variable in PowerShell:
     `$env:JAVA_HOME = (Split-Path (Split-Path (Get-Command javac).Source))`
     Verify with `javac -version` (must report 17.x or higher).

5. Error: "Port 8081 is already in use"
   - Cause: Another instance of BrewPOS or another web application is holding port 8081.
   - Solution: Change `SERVER_PORT=8082` in `.env` and restart the application, then navigate to `http://localhost:8082`.

2.4 ENGINEERING CHALLENGES, ROADBLOCKS & ARCHITECTURAL SOLUTIONS
--------------------------------------------------------------------------------
1. Roadblock: Preventing Past Receipt Totals from Changing when Menu Prices Change
   - Challenge: If an item's price is updated from 90.00 to 120.00, naive designs that join
     `order_line_item` with `menu_item.price` will retrospectively alter historical financial reports.
   - Solution: Designed `order_line_item` with a dedicated `sold_price DECIMAL(10,2)` column.
     At checkout time, the server copies the current `menu_item.price` into `sold_price`.
     Past receipts and daily sales reports always aggregate `quantity * sold_price`, guaranteeing
     historical audit immutability.

2. Roadblock: Handling Duplicate Item Additions under Composite Primary Key `(order_id, item_id)`
   - Challenge: Tapping the same menu item multiple times in the POS cart could trigger a database
     PK violation if multiple line items with the same `item_id` were transmitted.
   - Solution: Implemented duplicate merging in both client (`pos.js`) and server (`OrderService.java`).
     The backend iterates through requested items and uses a `LinkedHashMap` with `Math::addExact`
     to collapse duplicate line items into a single row with the combined quantity before persisting.

3. Roadblock: Floating-Point Rounding Errors in Financial Computations
   - Challenge: JavaScript IEEE 754 double-precision arithmetic causes inaccurate decimal representations
     (e.g., 0.1 + 0.2 = 0.30000000000000004).
   - Solution: Implemented integer-cent arithmetic in `api.js` (`toCents`, `formatMoneyFromCents`).
     All internal calculations use exact integer cents, formatting to 2 decimal places only at render time.
     In Java, all monetary values strictly use `BigDecimal` with explicit scale 2 and `RoundingMode.HALF_UP`.

4. Roadblock: Asynchronous UI Race Conditions on Rapid Date Filtering
   - Challenge: Clicking "Today" immediately followed by "All" could cause the slower initial HTTP
     request to resolve second, overwriting the user's latest selection with stale data.
   - Solution: Introduced monotonic request sequence counters (`listRequestSeq`, `reportRequestSeq`).
     When an asynchronous fetch resolves, it compares its local sequence token against the current
     active sequence; if superseded, the stale response is safely discarded.
